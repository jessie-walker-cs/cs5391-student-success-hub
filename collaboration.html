Engineering playbook

Three teams, shared standards.

Keep each component small, testable and accessible. Integrate through documented interfaces and clear responsibilities rather than making one team dependent on another's private work.

Team charter essentials

  1. Identify your team's subproject, proposed users, problem statement and minimum viable scope.
  2. Assign initial responsibilities and explain how they can rotate.
  3. Agree on meetings, communication channels, task tracking and response expectations.
  4. Choose GitHub repository arrangements and an issue/Jira board approved by the instructor.
  5. Document conflict resolution, code review, contribution evidence and escalation to the instructor.
  6. Define a shared approach to accessibility, testing, documentation, ethical use and data handling.

Shared engineering contract

The public project site provides the following recommended formats for integration planning; they are not completed student solutions.

  • Resource: id, title, category, description, url, tags, lastVerified.
  • Planner task: id, title, dueDate, status, notes (local fictional data).
  • Support outcome: scenarioId, recommendedResourceId, nextStep, disclaimer.

Keep IDs stable. Document any schema change in a shared issue or reviewed pull request before teams rely on it.

Working practices

  • Use descriptive commits and linked tasks.
  • Maintain a short team README and a definition of done.
  • Use documented pull-request reviews where feasible.
  • Demonstrate at least one functioning workflow every sprint.
  • Retain test logs and individual contribution evidence.
  • Ask the instructor before cross-team sharing of graded work.

Minimum integration

The hub home page links to each component. Each component runs independently and offers a way back to the hub. Teams coordinate interface names and example data, not shared grades.

Accessibility, security, and ethical boundaries

Accessible by default

Semantic headings, keyboard operation, clear labels, visible focus, readable text, meaningful feedback and responsive layouts. Use WCAG 2.2 guidance ↗ when designing tests.

No sensitive records

Use invented cases and public resource links. Do not collect student IDs, passwords, grades, financial details or actual support tickets in GitHub or your prototypes.

Professional attribution

Record what each person authored. Sharing agreed interface specifications is permitted for integration; exchanging completed graded solutions across teams is not permitted under the course syllabus without instructor authorization.
