Student Support Navigator

Turn common online-student problems into clear, actionable next steps.

Select this subprojectCollaboration standards

Problem and purpose

When a course or account problem occurs, students may not know which university office can help. A transparent guided troubleshooting tool can recommend appropriate public resources without collecting actual cases.

Scope and minimum viable product

Build an accessible decision-tree navigator for at least three fictional issue categories. Do not create tickets, collect private student data or provide binding interpretations of university policy.

Required capabilities

  • Offer categories such as sign-in, enrollment and course materials.
  • Present plain-language questions and provide back, restart and help options.
  • Explain recommendations and link to official university resources.
  • Offer an appropriate fallback when the problem is not covered.
  • Clearly label status demonstrations and test cases as fictional.

Example user journey

A student selects “Cannot see course in Canvas” and follows simple questions to an official assistance resource.

Development tasks across three Agile sprints

  1. Sprint 1: Define three fictional cases and implement an initial guided flow.
  2. Sprint 2: Add branching questions, navigation controls and safe fallbacks.
  3. Sprint 3: Connect Team 1 resource IDs, test all routing paths and improve usability.

Write detailed user stories, acceptance criteria and technical decisions in your team SRS and design document. This guidance supplements, but does not replace, Canvas rubrics.

Team roles and possible contributions

  • Scenario analyst: document common student problems and public office responsibilities.
  • Logic designer: model decision states, error handling and outcomes.
  • Interface developer: implement accessible controls and results.
  • Quality/ethics lead: test branch coverage, safety notices and fictional data.

Roles are responsibilities within the selected subproject. Students may rotate them while remaining on the same subproject team.

Acceptance criteria and testing

  • Each supported case reaches an understandable recommendation.
  • Back and restart work reliably.
  • Unknown cases offer a safe general-support option.
  • No UI states that a real ticket has been filed.
  • No genuine student records, access tokens or support requests are stored.

How this team works with the other two teams

  • Use Team 1 stable resource IDs for recommended support links.
  • Refer students to Team 2's planning guidance when deadlines are involved.
  • Share decision-tree interface specifications but never real student cases.

Optional enhancements

  • Printable next-steps checklist with no personal information.
  • Resource ID consistency checker.

Optional work requires instructor approval and must not prevent a complete, tested minimum product.
